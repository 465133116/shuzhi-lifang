一 产品定义

数治理方是什么，不是什么

一句话定义

数治理方是一套社区制度型信用治理系统平台。它不替代物业已有的ERP、道闸、门禁——它在这些系统之上，建立一层制度规则层：让每一次服务都有证据、每一次履约都有记录、每一次违约都有后果。

核心比喻

给社区装一套「制度交通规则」——不是摄像头抓违章，而是让每个人知道规则、遵守规则、违约有记录。物业是「路面」，数治理方是「交规+驾照分」。传统智慧物业做的是给路面装摄像头，数治理方做的是让路上的人愿意遵守交规。

理论底盘

收费秩序 = 正当性 × 履约可信度 × 价值感知度 × 守约共识度 × 分类精准度。五个因子不是加法——是乘法。任何一个因子趋近于零，整体崩塌。传统物业只抓「分类精准度」一个因子，且用催收代替分类、用威胁代替沟通——方法全错。数治理方五个因子同时做功。

二 平台形态

三种部署模式，对应不同的社区治理阶段

● 当前

P1 物业入口模式

纯物业通道，工单优先切入。物业公司授权后，数治理方客服以物业名义接触业主——建工单、做回访、记标签。15个P1字段驱动，不依赖小程序行为数据。适用场景：物业公司在管、首次引入数字化治理。

○ 规划

双轨过渡模式

小程序上线后，📱行为轨道 + 🎧客服轨道并行，双轨独立计算后OR合并。适用场景：退管物业交接期——旧物业数据导入、新物业接管、业主关系重建。

○ 规划

全模式（在管）

六端全开，AI六类自动分类+信号强度+交叉模式+响应级别R0~R4+数字秘书SaaS。五因子同时做功，覆盖业主大会→物业→业委会→社区全链路。适用场景：成熟社区、多角色协同治理。

三 六端入口（系统形态）

数治理方没有物理硬件——它的「形态」是六个独立端口，各对应一类使用者，各有独立界面、独立权限、独立数据视图。六端通过 ecosystem-bridge.js 跨端通信。

四 核心基础设施

横跨六端的三套底层引擎——业主分类、双轨数据、数字秘书

业主分类系统 F·E·A·B·D·C 六类判定

基于实际交互数据实时判定，不是静态标签。判定流水线：F（独立通道）→ E → A → B → D → C（兜底），命中即停。
类别名称判定条件
F历史复杂型标签含诉讼/信访/媒体/公安关键词 → 独立判定通道 → 最高响应级别R4 → 三端同步标红
E对抗失信型拒接≥3次 或 攻击性语言 或 差评无理由 → 合并对抗信号 → R3响应
A合理争议型有未闭环工单 + 业主明确提出服务问题 → 暂停催缴 → 优先解决争议 → 工单闭环后重新分类
B现实困难型表达经济困难（大病/失业/低保/单亲…）→ 标记困难 → 差异化方案
D惯性失约型无争议但承诺≥2次未兑现 → 失约计数递增 → 衰减：7天-1/28天归零/登录即消除
C观望拖延型无明确信号 → 按通话结果分C1~C6子类型 → 兜底分类 → R0~R1响应

双轨数据架构

📱小程序行为轨道 与 🎧客服通话轨道独立计算，OR合并后走统一判定流水线。每轨保留独立快照，交叉验证防数据污染——一条轨道的脏数据不会污染另一条。
维度📱 小程序轨道🎧 客服轨道
核心问题业主做了什么业主说了什么
数据性质结构化行为数据非结构化对话数据
可独立产生A · E(攻击/差评) · C4 · C5B · D · E(拒接/拒缴) · C1~C3
不能产生B · D · C1~C3C5
衰减周期30天半衰（工单类标签）14天半衰（通话类标签）
交叉影响登录→D消除；有工单→E拒接修正新备注→覆盖旧备注（B消除）

五因子乘法模型

收费秩序 = 正当性×履约可信度×价值感知度×守约共识度×分类精准度。传统物业只做「分类」一个因子——且用催收代替分类，方法全错。数治理方五个因子同时做功，乘法效应远大于加法。

🔀

双轨数据架构

📱行为轨道 + 🎧通话轨道独立计算，OR合并。每条信号标注来源，交叉验证防污染。小程序做了什么事和客服说了什么话，两条线互不干扰。

🏷

六类精准分类

F·E·A·B·D·C六类，基于实际交互数据实时判定，不是静态画像。同一句话对E类和对B类完全不同——分类决定策略，不是脚本统一念。

⚖

治理，不是催收

禁滞纳金威胁、禁门禁恐吓、禁信用施压。客服说「你遇到了什么问题」而不是「你欠了多少钱」。把焦点从欠费转移到服务——这是理念差异，不是话术差异。

👩‍💼

数字秘书 SaaS 多小区

秘书不必是业主（36号文立法区分+沪住建复确认）→ 一个秘书可服务多个小区 → SaaS模式低成本覆盖。法律+商业双重壁垒。

🔌

开放端口架构

六端各自独立接入，ecosystem-bridge跨端通信。不是封闭SaaS——灵石的摄像头能接、物业ERP能接、政府网格系统能接。是社区治理的基础设施层。
