# 数治理方 · 政府端运行逻辑说明

（业务版 · 不含代码）

---

## 一、总体架构

政府端由两个独立端口组成，分别对应政府治理体系中的两个层级：

| 端口 | 治理层级 | 定位 | 功能模块 |
|------|---------|------|---------|
| 街道端 | 第二层 · 街镇执行协调层 | 承接实施者 | 归集看板、预警接收、街道处理事件、资源下沉、指导台账、条块协同 |
| 区级端 | 第三层 · 区市管理决策层 | 调配者 + 验收者 | 态势仪表盘、预警中心、资源统筹调配、区级信号（五层模型） |

---

## 二、数据分级与归集机制（L1-L4）

政府端不采集原始数据，只接收经分级的**信号数据**。分级决定政府能看到什么、看不到什么：

| 级别 | 内容 | 政府端可见性 |
|------|------|-------------|
| L1 个人隐私 | 房号、姓名、电话、缴费明细 | 不出社区，政府端不可见 |
| L2 内部博弈 | 个别纠纷、调解过程、内部表决、议事讨论 | 不出社区，仅以脱敏统计形式归集展示 |
| L3 治理记录 | 工单记录、评价结果、信用记录、合同信息 | 依约归集，标准化输出（治理统计实时 / 信用·资金月度） |
| L4 统计汇总 | 履约率统计、满意度均值、异常占比、趋势分析 | 可公开共享，用于决策与态势研判 |

### 归集机制（治产数用）

| 数据类型 | 归集方式 | 频率 | 用途 |
|---------|---------|------|------|
| 治理运行统计（工单数/履约率/满意度均值） | 系统自动归集 | 实时 | 态势研判 · 资源下沉 |
| 异常事件标记（公共收益骤降/电梯逾期未检等） | 系统自动推送 | 实时 | 法定监管预警 |
| 信用记录（物业履约评级/供应商信用） | 系统自动归集 | 月度 | 信用监管 · 市场参考 |
| 公共收益/维修资金使用记录 | 系统自动归集 | 月度 | 法定资金监管 |
| 社区自治决策记录（议事/表决/公示） | 社区主动报备 | 事后 | 街道指导职能的信息基础 |

核心原则：**治产数用 · 一次采集 · 依法共享 · 最小必要**——数据是治理活动的自然沉淀，不是专项填报。

## 三、街道端六模块运行逻辑

### 1. 归集看板

- **小区信号灯**：每张小区卡显示信号灯（绿=常态、黄=关注、红=预警、蓝=需求），由预警接收/资源下沉模块**实时推导**——预警闭环或误报后，小区自动回落常态。信号灯不是人工设定，是其他模块状态的投影。
- **公共资金月度归集表**：五小区公共收益/维修资金/公示状态；资金异常标记（如公共收益骤降）与预警中心联动。
- **自治决策报备清单**：社区报备的议事/表决事项，街道可点"接收"（接收即确认，事后型信息）。
- **本页红线**：只呈现、不操作、不排名（报备清单的"接收"除外）。

### 2. 预警接收

街道辖区预警信号（红/黄两级）的接收与处置入口。每条预警有状态标签与处置路径：

- **待响应**（初始）：可"安排社区处理""街道直接处置""发起吹哨""标记误报"
- **已吹哨**：已转条块协同，等区级部门响应
- **自行处理中 / 社区处理中**：处置进行中，可"处理完成"闭环或"街道收回"（回待响应）
- **已标记误报**：误报解除
- **已闭环**：处置完成归档
- **街道处理不了 → 上报区级**：信号转入区级预警中心，街道端不可见该信号（移交）

### 3. 街道处理事件

由预警接收转入"街道直接处置"的事件汇聚在此，展示事件、所属科室、处置时限、状态。操作闭环后从列表消失（进归档）。

### 4. 资源下沉

区级审批下达的资源调配任务，街道在此**承接实施**：

- 状态链（街道视角）：已调配 → 承接 · 派遣 → 实施完成 → **待区级验收**
- 承接时选择派遣人员（可多选，5 人名单）、完成时限
- 标记完成后需求不直接归档，而是进入"待验收"，**由区级验收通过后才算归档**

### 5. 指导台账

街道开展上门指导的记录台账。资源下沉实施完成时自动生成一条台账记录，也可手动添加。记录指导对象、事项、方式、结果、背景。

### 6. 条块协同（吹哨）

街道处理不了的跨部门事项，向区级部门"吹哨"：

- 吹哨部门 8 个：区住建局、区市场监管局、区消防救援大队、区城管执法局、区公安分局、区卫健委、区生态环境局、区应急管理局
- 吹哨后事项状态为"已响应"，等待部门回传结果
- **部门响应回传后系统自动闭环**——街道不手动标记闭环；系统不设自动定时器，状态只随实际回传操作流动

## 四、区级端四模块运行逻辑

### 1. 态势仪表盘

全区治理态势纯呈现页。顶部四张统计卡为全区信号分布，每张卡下方标注**构成口径**：

- 🟢 常态小区：无在途信号
- 🟡 关注小区：文昌街道在途 + 明湖/临江街道基线
- 🔴 预警小区：区级预警中心在途 + 街道处置中
- 🔵 需求小区：资源统筹调配在途条数

按街道分布表定位信号集中的街道；趋势图看全区近 6 月闭环率与满意度走向。

### 2. 预警中心

- **来源**：街道上报的预警信号 + 区级法定监管自动推送
- **状态**：待处置 → 已推送科室核实 → 已转入资源统筹调配 → 已闭环（归档）
- **处置路径**：区级可"推送科室核实"（8 个区级职能部门）；**区级不直接处置**，处置方式是通过资源统筹调配发起调配任务
- 已闭环预警进入归档列表，留痕完整可追溯

### 3. 资源统筹调配

区级核心职权模块，完整链路：

1. **发起**：从预警中心在途预警中选择（**可多选**，每条预警生成一条调配任务），选择**推送科室**（可多选、联合承办）、**资源类型**（现场质询/调研走访/业务培训/政策辅导/专业核查/法律援助/矛盾调解/设施评估/**其他**，共 9 类）、填写理由
2. **审批 · 调配下达**：调配街道只读展示（系统映射，不可改），推送科室只读确认（发起时已确定），填写审批意见 → 下达街道承接
3. **街道承接实施**：街道选择派遣人员（可多选）与时限，实施后标记完成
4. **区级验收**：验收通过 → 需求归档 + **关联预警同步闭环**；退回补充 → 需求回到"已派遣"
5. **暂缓 / 不派遣**：需求终止进归档，**关联预警退回"待处置"**，可重新发起调配

去重规则：已有在途调配任务关联的预警，不再出现在发起列表。

### 4. 区级信号（五层模型）

政府端全部数据信号的总览页，按**五层模型**归类：

| 层 | 名称 | 回答的问题 | 内容 |
|----|------|-----------|------|
| ① | 共有功能合规运行 | 能不能这样用 | 消防、电梯、坠物等合规类信号 |
| ② | 共有权益维护与责任治理 | 谁受损、谁负责 | 公共收益、履约评级等权益类信号 |
| ③ | 共有功能体验优化 | 怎么才能更好用 | 满意度、投诉等体验类信号 |
| ④ | 共有事务协商共治 | 如何持续接受这套秩序 | 议事、报备等共治类信号 |
| ⑤ | 信用记录 · 分层共享 | 信源于事实 | 四维信用（物业/业委会/供应商/居民）、分层共享、正向激励、共享红线 |

- 前四层只展示**在途信号**，已闭环信号折叠在每层底部（点击展开）
- 第五层展示信用记录：前四层信号的处置闭环沉淀为过程信用——无承诺不评价、无证据不判断、无复核不生效、修复通道永久开放
- 本页无操作按钮，处置在各功能模块进行

## 五、需求全生命周期（核心链路）

资源统筹调配任务（需求）的完整状态链：

```
待审批 → 已调配 → 已派遣 → 待验收 → 已完成（归档）
   ↓            ↓
  暂缓 / 不派遣（归档，关联预警退回待处置）
```

### 职权边界（硬性规则）

| 动作 | 谁能做 | 街道端 | 区级端 |
|------|--------|--------|--------|
| 审批 · 调配下达 | 区级 | ✗ | ✓ |
| 暂缓 / 不派遣 | 区级 | ✗ | ✓ |
| 承接 · 派遣 | 街道 | ✓ | ✗ |
| 标记完成 | 街道 | ✓ | ✗ |
| 验收通过 / 退回补充 | 区级 | ✗ | ✓ |

越权操作会被系统拦截并提示，两端各自只显示自己有权限的动作按钮。

### 验收归档规则

- 街道"标记完成"后，需求进入**"待验收"**（黄色标签），**不直接归档**
- 区级"验收通过"后：需求归档（已完成）+ 若有关联预警，**预警同步闭环并归档**
- 区级"退回补充"后：需求回到"已派遣"，街道补充实施后重新标记完成

## 六、预警状态与闭环规则

### 区级预警状态

| 状态 | 含义 | 可恢复路径 |
|------|------|-----------|
| 待处置 | 初始在途 | 推送科室核实 / 发起资源统筹调配 |
| 已推送科室核实 | 已转区级职能部门 | 可转入资源统筹调配 / 归档 |
| 已转入资源统筹调配 | 已关联调配任务 | 任务验收通过 → 已闭环；任务暂缓/不派遣 → 退回待处置 |
| 已闭环 | 处置完毕 | 归档（不可逆） |

### 闭环三路径

1. **调配任务验收通过** → 预警同步闭环（留痕"资源统筹调配闭环"）
2. **暂缓/不派遣** → 预警退回"待处置"（可重新发起，不会死锁）
3. **推送科室核实后标记闭环** → 归档

## 七、条块协同运行逻辑

- 街道对跨部门事项发起吹哨（8 个区级部门）
- 吹哨单进入"已响应"状态，等待部门处理
- **部门响应回传后系统自动闭环**——街道没有手动闭环按钮
- 系统不设自动定时器、不模拟部门响应——状态只随用户的实际操作流动，保证演示的每一步都是真实点击产生的

---

## 八、留痕与佐证规则

### 全操作留痕

每一项处置操作都生成留痕记录，包含：时间、操作人、动作、备注。留痕不可删除，全链路可追溯。需求详情弹窗展示**全流程留痕**（每条含附件），是完整的处理档案。

### 全操作佐证上传

所有处置动作均支持上传佐证材料（最多 5 个，图片/文档）：

- 图片上传后显示缩略图，点击可全屏放大
- 附件随留痕全链路携带（留痕/详情/归档一致）
- 佐证是"无证据不判断"原则的落地——处置结论必须附有证据

---

## 九、治理红线（政府端不做的事）

- 不催报表、不看台账、不向下摊派数据采集
- 不排名、不评比（无法律依据的排名一律不做）
- 不直接向居委会下达行政命令（指导关系，非领导关系）
- 不替代业主大会做自治决策
- 居民个人信用信息不出社区（法律明确规定情形除外）
- 信用评级不用于无法律依据的社会性惩戒
- 信用记录保存期限、删除条件符合《征信业管理条例》
