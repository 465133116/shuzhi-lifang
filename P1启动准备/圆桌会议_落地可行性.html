📋 议题一：核心分配逻辑技术可行性

开发看过会议①②的决议后，逐一评估。
🖥️
🖥️ 开发工程师
我认真读完了两次会议的全部决议。先说结论：80%的逻辑可以直接实现，但有三个关键问题需要讨论。

✅ 可以直接做的：
• 每周选1250户 → 排序+取前N条。纯代码逻辑，没有任何障碍
• 轮流分配250户给5人 → 简单轮询
• 意向池50上限+手动拉入+满了踢 → CRUD操作
• 周三轮换回收 → 定时任务+批量更新
• 覆盖度加权(没打过的加分) → 查拨打记录表计数即可

❌ 有问题的：
🖥️
🖥️ 开发工程师 #问题1
"接通分级保留"依赖AI评分——但AI评分从哪来？

会议②决议：AI≥41或感受≥3的接通保留给原客服。
AI评分需要ASR语音转文字→NLP分析nt文本→输出1-100分。这是外部AI服务，不是写几行SQL能搞定的。

如果AI服务延迟了怎么办？如果AI还没算出来，轮换时间就到了？如果AI评错了？
📐
📐 量化分析师
AI评分延迟的问题我考虑过。方案：AI未就绪时用感受分临时替代。

通话结束后感受分是客服当场录入的，0延迟。AI评分可能需要1-30秒不等。如果轮换时AI还没算出来→先按感受分判定。感受≥3的保留，<3的释放。AI算出来后补录，但不影响已做的分配决策。

至于AI评错——保留不是永久决定。错了就错了，下次通话AI会重新评分。2周无进展也会自动释放。
🖥️
🖥️ 开发工程师 #问题2
"每周一选1250户"——周一早上8:30全员等着名单开工。计算5000户×四维排序需要多久？

初步估算：5000户×4个维度查表+计算=一秒钟内。但加上ASR回调、AI评分异步更新、覆盖度实时刷新——高峰时可能有并发问题。

建议：排序计算在周日晚上跑，周一早上直接读缓存。
流程：周日22:00 → 全量排序 → 写死前1250名 → 周一8:30客服打开即用。
⚙️
⚙️ 运营总监
周日22:00跑排序我同意。但我加一个场景：周三轮换是下午14:00，中午之前就要把新排序跑完——客服14:30开工，等不了。

周日的排序可以慢(离线批处理)。周三的排序必须快(在线实时)——因为轮换后客服立即开工。
🖥️
🖥️ 开发工程师 #问题3
"保留+意向池共享50上限"——如果客服A已经把50个名额用满了，此时又接通了一个高意愿的业主，怎么处理？

弹窗："您已达50户保留上限。是否将当前通话的业主替换掉已保留的某户？"——但这打断了通话流程。
还是接通时不给客服选择，系统后台自动判断：新接通评分>保留名单中最低评分的→自动替换。

这是交互细节，但影响开发工作量。
🎧
🎧 客服代表
别自动替换。我刚跟这个人聊完，觉得他有戏——结果系统因为他分数不够高，自动把另一个我觉得更有戏的踢了？系统不知道我的直觉。

做法：弹窗提示"已达50上限"，列出当前保留名单中评分最低的3个，问客服替换哪个——或者"暂不保留，释放回主池"。一秒钟的事。

📋 议题二：数据依赖与外部服务

🖥️
🖥️ 开发工程师
我把整个分配逻辑用到的数据源梳理了一遍：

数据来源实时性依赖
金额+欠费区间导入数据静态无。导入时即有
拨打记录(覆盖度)呼叫系统回调准实时呼叫API
客服感受分(1-5)客服录入实时无。纯前端
AI评分(1-100)ASR→NLP异步(1-30秒)ASR服务+NLP模型
标签(F/E/A/B/D/C)AI分析nt异步(同AI评分)同AI评分
意向池状态客服操作实时无。纯CRUD
保留名单系统计算轮换时计算AI评分+感受分

核心依赖链：电话接通→ASR→NLP→AI评分+标签。如果这链条断了，整个分级保留逻辑就瘫了。
👔
👔 管理者
所以需要一个降级方案：ASR/AI挂了怎么办？

我的底线：挂了也要能工作。客服不能坐在那等AI。

降级时：AI评分和标签暂不可用→纯靠金额+覆盖度+感受分排序→接通的全保留(因为没法判断质量)→等AI恢复后补评分、补标签。
🖥️
🖥️ 开发工程师
降级方案可以实现。但我也必须说：第一期不做ASR/AI，只用感受分+金额——这是最务实的起步。AI评分和标签可以第二期接入，不影响基本流程跑通。

第一期的排序就三个维度：
排序分 = 金额(40%) + 覆盖度(35%) + 感受分(25%)
标签和AI评分预留接口，第二期补上。

📋 议题三：开发分期建议

🖥️
🖥️ 开发工程师
分期功能数据依赖工期
P0 主池→流动池→个人池。纯金额排序+轮流分配。意向池CRUD。周三轮换回收 金额+呼叫状态+感受分 2周
P1 覆盖度加权。接通分级保留。保留+意向共享50上限 P0数据+拨打记录计数 1周
P2 AI评分+标签接入。ASR→NLP→四维排序完整版 ASR服务+NLP模型 3周(含对接)
P3 管理者看板。流转日志。月度报表 全部数据 2周

P0先跑起来——客服能分配、能打电话、能记感受分、能拉意向池。AI评分后面接。
👔
👔 管理者
同意P0先行。但覆盖度加权能不能提到P0？否则前两周纯金额排序，后3750户还是打不到——等于浪费了两周。

覆盖度只需要计数"拨打过几次"——P0就有这个数据(呼叫回调)。不依赖AI。
建议：P0=金额+覆盖度+感受分+意向池+轮换。
🖥️
🖥️ 开发工程师
可以。覆盖度加权逻辑不复杂——查拨打记录表count一下。P0做到三维排序：
P0排序分 = 金额(40%) + 覆盖度(35%) + 感受分(25%)
P1再补接通分级保留和共享50上限。P2接入AI评分替换感受分中的一部分权重。

✅ 会议决议：开发落地方案

#决议通过
1P0一期(2周)上线：金额+覆盖度+感受分三维排序。三池流转。意向池。周三轮换。先跑起来。5/5
2P0降级方案：感受分即时可用(0延迟)。排序时AI未就绪→感受分替代。AI算出来后补录。5/5
3周日22:00预排序：周一1250名单提前算好。周三轮换前1小时重算。5/5
4保留满50时弹窗选择：客服选替换哪个或"暂不保留"。不自动替换。4/5
5P1(第3周)补接通分级保留。P2(第5周)接AI评分+标签。P3(第7周)管理者看板。5/5

⚠️ 风险清单

高
ASR服务不稳定
通话录音→语音转文字→如果ASR挂了或延迟>30秒，AI评分无法生成。降级方案已覆盖，但P2前不依赖ASR。
中
5000户排序性能
三维排序5000条<1秒。加上数据库查询、网络延迟，预估<3秒。离线跑可接受。但如果实时排序(轮换后)5000户同时并发，需加缓存。
低
覆盖度数据一致性
呼叫系统回调可能延迟/丢失。建议加兜底：如果回调30秒未到→前端直接标记"已拨打"。
