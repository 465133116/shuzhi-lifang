## 1. 项目概述

### 1.1 项目定位

**数字秘书系统**是数治理方平台中以"业委会秘书"角色为核心的操作系统。它基于沪房物业〔2026〕36号第6条赋予的政策合法性，将业委会秘书的日常职责数字化、工具化、可定制化，形成可复用到多个小区的SaaS化客服端口。

### 1.2 核心命题

| 维度 | 内容 |
|------|------|
| **做什么** | 将政策18条规定的业委会运作要求转化为12个可操作的数字化功能模块 |
| **给谁用** | 秘书（主操作者）、业委会委员、物业公司、居委/街镇（监督者）、业主（服务对象） |
| **怎么定制** | 每小区独立租户，议事规则/管理规约/流程/权限/品牌均可参数化配置 |
| **怎么部署** | 在管模式（12模块全开）、双轨模式（过渡期精简）、P1模式（4模块MVP） |

### 1.3 与现有系统的关系

```
数治理方平台
├── 业主分类系统（双轨V8.0）───→ 为秘书工作台提供业主画像
├── P1工单系统 ──────────────→ 工单协同模块复用+扩展
├── 短信系统（11条模板）──────→ 短信发送模块嵌入秘书工作台
├── ecosystem-bridge.js ─────→ 跨端口消息总线扩展至秘书端
├── 五端HTML原型 ────────────→ 新增"秘书端"为第六端
└── ★ 数字秘书系统 ──────────→ 本次新建（12模块 + SaaS定制层）
```

### 1.4 秘书角色的法律定位（关键）

**核心结论：秘书不必是业主。**

| 维度 | 业委会委员 | 业委会秘书 |
|------|-----------|-----------|
| **法律依据** | 36号文第4条 | 36号文第6条 + 沪住建建议复〔2018〕23号 |
| **身份要求** | "应当由……**业主担任**" | "可以**配备**"（未要求业主身份） |
| **产生方式** | 业主大会**选举** | 业委会**聘请** |
| **权力来源** | 全体业主投票授权 | 业委会合同授权 |
| **角色性质** | 决策者 | 执行者（行政辅助） |
| **经费来源** | 委员津贴（第9条） | 工作经费，由业主大会决定从公共收益或业主分摊列支（第13条） |
| **对外效力** | 代表全体业主 | 代表业委会（协助履行职责） |

**政策措辞对比（同一份36号文）：**

- 第4条（委员）："业主委员会委员应当由……**业主担任**" ← 明确要求业主身份
- 第6条（秘书）："业主委员会可以**配备秘书**" ← 仅说"配备"，未要求业主身份

这不是疏忽，是**立法层面的有意区分**。上海市住建委2018年对市人大建议的正式答复（沪住建建议复〔2018〕23号）进一步确认：

> "业主委员会可以根据工作需要**聘请专职秘书**，负责处理业主委员会日常事务，其具体产生办法、工作职责、所需经费由业主大会作出决定或在管理规约、业主大会议事规则中约定。"

**对系统设计的三个影响：**

1. **秘书可以外聘 → SaaS多租户成立**：宁波个信可聘请专业秘书，同时服务多个小区。切换小区 = 切换工作台租户。
2. **秘书≠决策者 → 权限边界清晰**：秘书端口只能执行（建单/记录/通知），不能决策（审批印章/表决/选聘）。
3. **秘书经费有据 → 商业模式闭环**：秘书薪酬从公共收益列支，平台工具费计入办公经费——资金链路合规。

每条政策条款 → 对应的系统功能模块 → 具体功能点。

| 条款 | 政策要求 | 对应模块 | 功能点 |
|:----:|----------|----------|--------|
| 第1条 | 业委会是执行机构，接受党组织领导 | 合规引擎 | 组织架构配置、党建对接模块 |
| 第2条 | 业主大会决策机制（选聘物业/维修资金/公共收益） | 会议管理 | 议题征集→表决→纪要全链路 |
| 第3条 | 街镇组建筹备组/换届改选小组 | 选举辅助 | 筹备组工具、时间线管理 |

| 第5条 | 候补委员制度（列席无表决权、得票递补） | 选举辅助 | 委员状态管理、递补触发 |
| **第6条** | **业委会职责 + 配备秘书 + 督促交费**<br>⚠️ 仅说"**配备**"，**不要求业主身份** | **秘书工作站（核心）+ 催缴辅助** | **来电弹屏、建单、短信、通话记录、催缴台账** |

| 第8条 | 信息公开（维修资金/公共收益/审计/合同） | 信息公开 | 财务公示、业主查询端 |
| 第9条 | 委员津贴、列入后备力量 | 培训管理 | 履职档案、津贴管理 |
| 第10条 | 物业选聘（招投标、统一平台、动态调价） | —（P3） | 物业选聘工具、招标管理 |
| 第11条 | 维修资金筹集使用（30%红线、审价约束） | 财务辅助 | 维修资金台账、审价单 |
| 第12条 | 公共收益管理（全额入监管账户、单独列账） | 财务辅助 | 公共收益台账、成本核算 |
| 第13条 | 工作经费规则 | 财务辅助 | 预算编制、支出审批 |
| 第14条 | 财务管理（代理记账/审计/审价） | 财务辅助 | 审计对接、代理记账接口 |
| 第15条 | 街镇培训、会议邀请居村、动态监测 | 培训管理 + 会议管理 | 参训记录、会议列席邀请、监督报告 |
| **第16条** | **业主接待日 + 月度联席会议** | **业主接待（客服核心）+ 会议管理** | **来电弹屏、咨询/投诉/建议三通道、接待排班、联席会议** |
| 第17条 | 履职约束（约谈/发函/赔偿/刑责） | 合规引擎 | 越权拦截、合规边界检测、约谈记录 |
| **第18条** | **物业治理委员会补位** | **模式切换（底座）** | **双轨模式切换、过渡期托管、补位工作台** |

★标注的为P1阶段优先实现条款。

## 3. 系统架构

### 3.1 四层架构

```
┌─────────────────────────────────────────────────────┐
│  第4层：外部对接层（可选集成）                          │
│  街镇备案 | 居委协同 | 房管局 | 物业系统 | 银行 | 短信通道  │
├─────────────────────────────────────────────────────┤
│  第3层：定制化配置层（每小区独立）                       │
│  小区身份 | 议事规则 | 流程模板 | 权限角色 | 品牌外观      │
├─────────────────────────────────────────────────────┤
│  第2层：核心功能模块（按需启用，12模块）                  │
│  业主接待 | 工单协同 | 催缴辅助 | 会议管理 | 信息公开       │
│  档案管理 | 印章管理 | 选举辅助 | 财务辅助 | 培训管理       │
│  短信发送 | 合规引擎                                    │
├─────────────────────────────────────────────────────┤
│  第1层：政策底座（不可定制—全市统一）                     │
│  合规引擎 | 标准流程库(SOP) | 格式文书库 | 法规知识库       │
└─────────────────────────────────────────────────────┘
```

### 3.2 模块依赖关系

```
合规引擎（底座，所有模块依赖）
    │
    ├── 业主接待 ──→ 依赖：业主分类系统、工单协同、短信发送
    │
    ├── 工单协同 ──→ 依赖：业主接待（建单入口）、短信发送（通知）
    │
    ├── 催缴辅助 ──→ 依赖：业主分类系统、短信发送
    │
    ├── 会议管理 ──→ 依赖：信息公开（决议公示）
    │
    ├── 信息公开 ──→ 依赖：会议管理（决议来源）、财务辅助（数据来源）
    │
    ├── 档案管理 ──→ 独立（可选依赖会议管理、印章管理）
    │
    ├── 印章管理 ──→ 独立
    │
    ├── 选举辅助 ──→ 独立（P3）
    │
    ├── 财务辅助 ──→ 独立（P3，可选依赖工单协同）
    │
    ├── 培训管理 ──→ 独立（P3）
    │
    └── 短信发送 ──→ 独立（被多个模块调用）
```

### 3.3 三种部署模式

| 模式 | 触发条件 | 秘书角色 | 启用模块 | 政策对齐 |
|------|----------|----------|----------|----------|
| **在管模式** | 业委会正常运作 | 全职/兼职业委会秘书 | 12模块全开 | 第1~17条 |
| **双轨模式** | 业委会换届交接/缺位 | 街镇物业治理委员会指定人员 | 印章/财务冻结，其余9模块 | 第18条 + 第4~5条 |
| **P1模式** | 业委会缺位，物业直连 | 物业客服/管家兼任 | 仅4模块（接待+工单+催缴+短信） | 第6条 + 第16条 |

#### 4.2.2 设计依据详解

**政策原文（第16条）**：
> 业主委员会在履职过程中要充分听取业主、使用人的意见和建议，接受业主的咨询、投诉和监督，每月至少安排一次业主接待日，及时协调、解决业主反映的问题。

**系统映射**：
- "充分听取意见和建议" → REC-03/04/05 咨询/投诉/建议三通道
- "接受咨询、投诉和监督" → REC-02 业主信息卡片（提供完整上下文）

#### 4.3.1 功能清单

| 功能ID | 功能名称 | 说明 | P1/P2/P3 |
|:------:|----------|------|:--------:|

#### 4.3.3 工单状态机

```
[draft] ──秘书提交──→ [pending] ──物业接单──→ [processing]
  草稿                   待处理                   处理中
                            │
                            │ 物业回单
                            ▼
                        [reviewing] ──秘书确认──→ [closed]
                          待确认                      已闭环
                            │
                            │ 驳回
                            ▼

[pending] ──超时──→ [overdue_pending] ──自动升级
[processing] ──超时──→ [overdue_processing] ──自动升级
```

## 9. 技术选型建议

### 9.1 当前约束

- 现有技术栈：纯原生 HTML/CSS/JS，localStorage + BroadcastChannel
- 无后端服务器，无数据库
- 键前缀：`sgzf_`
- 跨端口通信：BroadcastChannel (ecosystem-bridge.js)

### 9.2 P1阶段（保持现有架构）

| 层面 | 方案 |
|------|------|
| 前端 | 原生 HTML/CSS/JS，新增"秘书端"端口 |
| 数据 | localStorage（`sgzf_sec_*` 前缀扩展） |
| 跨端口 | BroadcastChannel，新增 `secretary` channel |
| 数据隔离 | localStorage key 加入 `community_id` 前缀 |
| 离线 | 单机运行，数据导出/导入 JSON |

### 9.3 P2/P3阶段（演进方向）

| 层面 | 方案 |
|------|------|
| 后端 | Node.js (Express/Fastify) 或 Python (FastAPI) |
| 数据库 | PostgreSQL（多租户：schema 隔离或 row-level security） |
| 前端 | 保持原生或迁移至 React/Vue（渐进式） |
| 实时通信 | WebSocket（替代 BroadcastChannel） |
| 文件存储 | 本地文件系统或 OSS |
| 认证 | JWT + RBAC |
| 短信 | 阿里云/腾讯云 SMS API |
| CTI | 第三方CTI中间件或自建WebRTC |
