# 小程序端 · 业主分类逻辑

> 数治理方 P1 · 2026-06-30
> 本文档描述仅基于小程序数据的业主分类判定逻辑。
> 小程序端独立运行，不依赖客服通话数据。

---

## 一、小程序端能拿到什么数据

小程序端只能拿到业主在小程序上的行为数据，拿不到客服通话内容。

| 数据项 | 含义 | 取值 |
|--------|------|------|
| li | 业主是否登录过小程序 | 是 / 否 |
| 工单列表 | 每条工单含以下字段 | — |
| ——tp | 工单类型 | 报修 / 投诉 / 建议 |
| ——st | 工单状态 | 待处理 / 处理中 / 待验收 / 已完成 |
| ——rt | 满意度评分 | 1~5 星（仅已完成工单有） |
| ——差评原因 | 差评原因 | 问题没解决 / 态度不好 / 太慢 / 其他 |
| ——de | 工单描述文本 | 自由文本 |
| ——sr | 工单来源 | 业主自提 / 客服草稿 |
| ——ca | 问题分类 | 水管漏水 / 电梯故障 / … |
| ——ct | 工单创建时间 | 日期 |
| lb | 特殊标签 | 自由文本（如"已搬家""出租"） |

## 二、小程序端能判断什么、不能判断什么

| 信号 | 小程序端能判断吗 | 说明 |
|:----:|:---------------:|------|
| **F** | ✗ 不能 | F 信号依赖 lb 标签。lb 由客服标注，但小程序端可以读取已标注的 lb |
| **E** | △ 部分能 | 能判断攻击性投诉工单（E2）和态度差评累积（E4）。不能判断拒接和拒缴 |
| **A** | ✓ 能 | 核心能力。基于工单状态判断 |
| **B** | ✗ 不能 | B 信号依赖通话内容中的困难关键词，小程序端没有通话数据 |
| **D** | ✗ 不能 | D 信号依赖通话中的承诺行为。但小程序端的 li 数据可以触发 D 消除 |
| **C1~C3** | ✗ 不能 | 依赖通话内容中的从众/拖延/对比关键词 |
| **C4** | ✓ 能 | 基于历史评分和投诉工单存在性判断 |
| **C5** | ✓ 能 | 基于 A 消除事件自动产生 |
| **C6** | ✓ 能 | 兜底：无任何可判断的信号时 |

## 三、小程序端可独立检测的信号

### 信号一：A 信号（有具体争议）

判断逻辑：
- 遍历该业主所有工单
- 如果存在任意一条工单同时满足：
  - 工单类型 = "报修" 或 "投诉"
  - 工单状态 ≠ "已完成"
- → A = 有
- 否则 → A = 无

补充：
- 客服草稿（来源=客服草稿）也计为工单
- 但如果同一问题业主已自行提交，草稿不重复计入
- 建议类工单不触发 A

**A 信号消除（工单闭环事件）：**
| 条件 | 结果 |
|------|------|
| 修后照片 ✓ + 处理结果 ✓ + 满意度 ≥ 3 星 | A 消除 |
| 差评原因 = "问题没解决" | A 保持，工单重开 |
| 差评原因 = "态度不好" | A 消除，态度差评计数 +1 |
| 差评原因 = "太慢" | A 消除，失约计数 +1 |
| 修后照片缺失 | A 保持 |

---

### 信号二：E 信号（对抗态度·仅攻击型/差评型）

**子规则一：攻击性投诉检测**
- 遍历工单描述文本（de）
- 如果包含攻击性关键词（辱骂、威胁等）→ E2·攻击型

**子规则二：态度差评累积检测**
- 统计已完成工单中，满意度 = 1-2 星 且 差评原因 = "态度不好" 的数量
- 数量 ≥ 3 → E4·差评累积型

**小程序端不能判断的 E 子类型：**
- E1·拒接型（需要通话拒接数据）
- E3·拒缴型（需要通话内容数据）

---

### 信号三：C4 信号（信任缺失）

判断逻辑（三个条件同时满足）：
- 历史工单中存在满意度为 1-2 星的记录
- 不存在类型为"投诉"的正式工单（业主有不满但没正式投诉）
- 当前无 A 信号（所有工单已闭环）

→ C4 = 有

---

### 信号四：C5 信号（已解决过渡态）

判断逻辑：
- 历史上曾有过 A 信号（曾有过未闭环工单）
- 当前 A / E / F 信号全部为无
→ C5 = 有

---

### 信号五：C6 信号（信息不足）

判断逻辑：
- A / E / C4 / C5 全部为无
- 无工单记录
- → C6 = 有

---

## 四、小程序端分类结果（不完整分类）

由于小程序端只能看到部分信号，它给出的分类是不完整的。对于小程序端无法判断的信号，标记为"未知"。

### 小程序端主分类判定（简化版）

按以下顺序检查小程序端能判断的信号：

| 步 | 检查 | 命中→主分类 | 说明 |
|:--:|------|:----------:|------|
| ① | E 信号 = 有？ | E | 仅 E2 攻击型 或 E4 差评累积型 |
| ② | A 信号 = 有？ | A | 有未闭环工单 |
| ③ | 无 A/E → C 细分 | C | 走下方 C 类判定 |

**C 类判定：**
| 步 | 检查 | 命中→子类型 |
|:--:|------|:----------:|
| 1 | 有 A 消除记录且当前无 A/E | C5·已解决 |
| 2 | C4 信号 = 有 | C4·信任缺失 |
| 3 | 无任何信号 | C6·信息不足 |

### 小程序端无法判断的信号（标记为"未知"）

| 信号 | 原因 |
|:----:|------|
| F | 需要 lb 标签（由客服标注），但小程序端可读取已标注的值 |
| B | 需要通话内容中的困难关键词 |
| D | 需要通话中的承诺行为数据 |
| E1 | 需要通话拒接数据 |
| E3 | 需要通话中拒缴表述 |
| C1~C3 | 需要通话内容中的从众/拖延/对比关键词 |

## 六、A 信号子类型判定

小程序端可独立判定 A 类的以下子类型：

| 子类型 | 条件 |
|:------:|------|
| A·报修型 | 报修工单 ≥ 1 且 投诉工单 = 0 |
| A·投诉型 | 投诉工单 ≥ 1 且 报修工单 = 0 |
| A·混合型 | 报修工单 ≥ 1 且 投诉工单 ≥ 1 |
| A·反复型 | 同一问题分类（ca）的工单 ≥ 3 次 |
| A·高优先级型 | 未闭环工单 ≥ 3 或 最早未闭环超 SLA 7 天以上 |
| A·首次型 | 历史上无 A 消除记录 |

## 七、小程序端能做的辅助计算

### 信号强度（仅小程序端有数据的信号）

| 信号 | 得分计算 |
|:----:|------|
| A 得分 | 未闭环数 × 40 + 报修总数 × 15 + 投诉总数 × 20 − 平均满意度 × 10（上限100） |
| E 得分 | 攻击投诉次数 × 35 + 态度差评次数 × 20（上限100） |

### 轨迹追踪（仅基于小程序端分类历史）

- 近 3 次小程序端分类
- 趋势（向好/稳定/向坏）
- 新鲜度（最近工单距今时间）

## 八、小程序端与客服端的关系

```
┌─────────────────┐     ┌─────────────────┐
│   小程序端分类    │     │   客服端分类      │
│                 │     │                 │
│  能判断:         │     │  能判断:         │
│  A ✓           │     │  B ✓           │
│  E(攻击/差评) ✓ │     │  D ✓           │
│  C4 ✓          │     │  E(拒接/拒缴) ✓ │
│  C5 ✓          │     │  C1~C3 ✓       │
│  C6 ✓          │     │                 │
│                 │     │  不能判断:       │
│  不能判断:       │     │  A ✗           │
│  B ✗           │     │  C4 ✗          │
│  D ✗           │     │  C5 ✗          │
│  E(拒接/拒缴) ✗ │     │                 │
│  C1~C3 ✗       │     │                 │
└────────┬────────┘     └────────┬────────┘
         │                       │
         └───────────┬───────────┘
                     ▼
         ┌─────────────────────┐
         │     合并引擎          │
         │   OR 逻辑合并        │
         │   完整分类输出        │
         └─────────────────────┘
```

小程序端分类 ≠ 最终分类。小程序端只提供它能判断的部分，标记不能判断的信号为"未知"。客服端同理。两个不完整分类交给合并引擎，取 OR 后得到完整的六信号状态，再走统一判定流水线。

---

> **关键要点：**
> 1. 小程序端只能基于工单数据做判断
> 2. B/D/E1/E3/C1~C3 这些需要通话内容的信号，小程序端标记为"未知"
> 3. 小程序端给出的分类是"不完整分类"，需要后续与客服端数据合并
> 4. 小程序端最重要的独立能力：检测 A 信号和 A 消除条件
