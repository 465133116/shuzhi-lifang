# 数治理方 · 近场供应链端 产品设计文档

*最后更新：2026-07-28*

## 一、端口概述与定位

近场供应链端是数治理方七端生态中的供应保障端，业委会与物业服务中心共用。供应链端只负责供应商的发现与筛选——用API数据从周边把合格供应商找出来、筛出来、管起来，不参与具体比价和采购决策。比价和供应商选择由物业端和业委会端根据自身需求自主完成。

「近场」的核心含义：以小区为圆心，辐射周边就近的供应体系——用API大数据从社区周边把合格供应商筛出来，织成一张信用网。这不是一个"采购流程管理工具"，独特价值在于：

| 价值维度 | 说明 |
|----------|------|
| 供应商发现 | API从周边主动扫描，不等推荐 |
| 供应商筛选 | 六层数据漏斗，不靠人脉靠数据 |
| 信用持续监控 | 外部API每日扫描，风险前置预警 |
| 供应商匹配 | 按品类资质自动匹配合格供应商，不替代人工比价决策 |

### 1.2 「近场」的半径逻辑

- 日常维保（水电/保洁/绿化）：3公里内，30分钟到
- 专业维修（电梯/消防/防水）：本市资质企业，2小时响应
- 大修改造（电梯更换/外墙翻新）：放宽至全省/全国，以资质和业绩优先

## 二、近场供应商发现与筛选机制（核心）

### 2.1 六层数据漏斗模型

| 层级 | 名称 | 作用 | 数据来源 |
|------|------|------|----------|
| L1 | 工商基础层 | 存续状态·经营范围·注册资本 | 工商API |
| L2 | 资质认证层 | 行业资质·专业人员证书·保险 | 政府/协会API |
| L3 | 行政合规层 | 纳税信用·社保缴纳·行政处罚 | 税务/人社/市监API |
| L4 | 司法风险层 | 被执行人·失信·裁判文书 | 司法公开API |
| L5 | 履约评价层 | 历史履约·用户评价·响应速度 | 平台内部数据 |
| L6 | 动态监控层 | 舆情·招聘动态·经营异常 | 多源API实时扫描 |

L1-L4筛掉不合格的（从几百家→几十家），L5-L6在合格供应商中排序推荐。每一层都是可独立验证的数据来源，不依赖人工判断。

### 2.3 两种扫描模式

| 模式 | 触发方式 | 适用场景 | 响应时间 |
|------|----------|----------|----------|
| 主动扫描 | 定时任务（每日/每周） | 定期更新候选池 | 全天 |
| 事件驱动 | 新采购需求提交 | 紧急维修、专项采购 | 30分钟内 |

### 2.6 关键行政数据详解

行政合规层（L3）是采购风险的早期预警信号——在企业真正出事之前，行政数据就已经开始恶化：

| 行政数据类型 | 含义 | 如何影响供应商评估 |
|-------------|------|-------------------|
| 纳税信用评级 | A/B/C/D/M级 | D级自动排除，C级标记"税务风险" |
| 社保缴纳率 | 实际缴纳人数/工商登记人数 | <70%标记"用工不稳定" |
| 经营异常名录 | 地址异常/年报未报 | 列入即暂停新单 |
| 行政处罚 | 市监/安监/环保处罚 | 近2年>3条标记"合规高风险" |

## 三、采购信息流通机制

### 3.2.1 三级透明体系

| 层级 | 可见范围 | 可见内容 |
|------|----------|----------|
| L1·全小区公开 | 全体业主 | 采购项目名称·中标供应商·合同金额·履约评分 |
| L2·决策层可见 | 业委会+物业经理 | L1全部+供应商资质·审批意见 |
| L3·监管层可见 | 社区端 | L2全部+供应商信用分·合规检查结果 |

设计原则：透明度不是"所有信息对所有人公开"——按角色定可见范围，闭环后自动公示。

## 四、供应商进出与监管机制

### 4.3 准入门槛

| 维度 | 要求 |
|------|------|
| 工商 | 存续≥1年，无经营异常 |
| 资质 | 具备行业要求的许可证和专业人员 |
| 行政合规 | 纳税信用≥C级，社保缴纳率≥70% |
| 司法 | 无失信被执行记录 |
| 地域 | 符合"近场"半径要求 |

### 4.5 退出机制

| 退出类型 | 触发条件 | 处理 |
|----------|----------|------|
| 自然淘汰 | 连续6个月无新单 | 移出活跃候选池→保留归档 |
| 信用触底 | 信用分降至<40 | 自动停用，3个月内不可重新申请 |
| 严重违规 | 重大质量事故/安全事故/欺诈 | 永久拉黑+全平台标记 |

## 五、采购合规性监管机制

### 5.1 五道合规闸

| 闸门 | 检查内容 | 异常处理 |
|------|----------|----------|
| 预算闸 | 采购金额是否在预算额度内 | 超额阻止，需业委会追加预算 |
| 审批闸 | 是否通过对应层级审批 | 未审批阻止，无例外 |
| 拆单闸 | AI检测是否拆分大单规避审批 | 识别→标记→推送业委会审查 |
| 利益冲突闸 | 供应商与决策人是否有关联 | 关联→回避→推送备选供应商 |

## 六、供应商信用监管机制

### 6.1 信用评分模型

供应商信用分 = 外部信用基准(40%) + 内部履约表现(60%)

| 维度 | 权重 | 指标 |
|------|------|------|
| 外部信用基准(40%) | 25% | 工商状态·纳税信用 |
| | 15% | 司法风险·行政合规 |
| 内部履约表现(60%) | 20% | 验收质量 |
| | 15% | 响应速度 |
| | 10% | 评价满意度 |
| | 5% | 履约频次 |

### 6.2 信用分应用

| 信用分区间 | 标签 | 影响 |
|-----------|------|------|
| 90-100 | A级·推荐 | 排序置顶，优先推荐 |
| 75-89 | B级·正常 | 正常参与 |
| 60-74 | C级·待评估 | 新单暂停，标记审查 |
| <60 | D/E级·限制/淘汰 | 自动停用 |

## 七、与生态其他端口的关系

| 关联端口 | 接收 | 输出 |
|----------|------|------|
| 物业端 | 采购需求·供应商选择·验收记录 | 候选池匹配·信用分·供应商列表 |
| 业委会端 | 审批决策·供应商激活确认 | 候选池数据·信用报告 |
| 社区端 | 监督查询 | 采购记录·合规审计数据 |
| AI端 | — | 供应商筛选·信用计算·拆单检测 |

## 八、近场供应链 vs 传统物业采购

| 维度 | 传统物业采购 | 数治理方近场供应链 |
|------|-------------|-------------------|
| 供应商发现 | "熟人推荐/五金城" | API扫描→六层漏斗筛选 |
| 供应商评估 | "上次那个老张还行" | 工商+行政+司法+资质+履约→实时信用分 |
| 供应商选择 | "熟人推荐/五金城" | 六层漏斗筛选+信用排序 |
| 合规保障 | "经理自己把关" | 五道自动合规闸 |
| 供应商管理 | "这次不行下次不找他" | 信用分驱动的自动排序/限制/淘汰 |
