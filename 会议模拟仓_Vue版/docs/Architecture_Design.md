# 业主会议系统微服务与安全架构设计文档

## 1. 架构概览 (Microservices Architecture)
为了满足高并发（QPS > 500）与低延迟（接口响应时间 < 200ms）的需求，业主会议系统后端采用 **Spring Cloud Alibaba / Go-Micro** 微服务架构，结合 K8s 容器化部署。

### 1.1 核心微服务划分
- **API 网关 (Gateway)**：基于 APISIX，负责路由转发、限流熔断、鉴权拦截。
- **身份认证服务 (Auth Service)**：提供基于 OAuth2.0 / JWT 的多级权限控制（普通业主、业委会、管理员），对接人脸识别与实名认证接口。
- **会议核心服务 (Meeting Service)**：负责会议室创建、状态流转、议程管理。
- **实时信令服务 (Signaling Service)**：基于 WebSocket / WebRTC，处理实时投票、举手、聊天等低延迟交互（独立横向扩容以支撑 QPS > 500）。
- **媒体处理服务 (Media Service)**：对接流媒体服务器（如 SFU 架构的 mediasoup），负责音视频分发与云端录制。
- **AI 智能服务 (AI Service)**：集成语音转文字（ASR）与 NLP 大模型，实现会议纪要自动生成与决议提取。
- **通知中心服务 (Notification Service)**：统一处理短信、邮件、App 推送，维护投递状态与已读回执。
- **审计日志服务 (Audit Service)**：基于 ELK / ClickHouse，异步收集所有核心操作日志。

## 2. 高并发与高可用设计
- **缓存策略**：使用 Redis Cluster 缓存会议基础信息、用户会话、权限树；热点数据（如实时票数）使用 Redis Pipeline 聚合更新，每秒同步至 MySQL。
- **消息队列**：采用 Kafka 解耦峰值流量，如投票动作先入队后落库，确保极端并发下数据库不被击垮。
- **数据库**：MySQL 8.0 采用主从架构（一主多从），读写分离；票数等高频数据采用分表分库设计。
- **限流降级**：通过 Sentinel 在网关层进行 IP 和 User 级别的 QPS 限制，接口响应超时则触发降级返回缓存数据或提示。

## 3. 等保三级安全合规设计
为满足**信息系统安全等级保护（三级）**要求，在架构中深度融合以下安全机制：
1. **身份鉴别**：支持双因子认证（密码+短信验证码/动态口令），登录失败锁定机制（如 5 次锁定 30 分钟）。
2. **访问控制**：基于 RBAC 模型的强制访问控制，接口级别权限校验，防止越权操作。
3. **数据加密**：
   - 传输层：全站 HTTPS (TLS 1.2+)，关键信令采用 WSS 协议。
   - 存储层：业主隐私数据（身份证、人脸特征、手机号）采用 AES-256-GCM 加密存储，密钥由 KMS（Key Management Service）统一管理。
4. **安全审计**：操作日志完整记录操作人、时间、IP、动作、结果。日志不可篡改，保存周期不少于 6 个月。
5. **抗攻击能力**：部署 WAF 防御 SQL 注入、XSS 攻击；网关层防御 DDoS 攻击与重放攻击（依赖请求时间戳与 Nonce 防重放）。

## 4. 插件化扩展机制 (Plugin Mechanism)
系统采用 **SPI (Service Provider Interface)** 架构设计，支持在不修改核心代码的情况下扩展功能：
- **定义标准接口**：如 `IVotingPlugin`, `IMinutesExporterPlugin`。
- **动态加载**：通过配置中心（Nacos/Apollo）动态启用/禁用插件。
- **示例场景**：可随时接入第三方区块链存证插件，将会议决议一键上链，或接入第三方电子签章插件。
