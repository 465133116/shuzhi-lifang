〇 产品定义与平台形态

数治理方是什么、怎么部署

一句话定义

数治理方是一套社区制度型信用治理系统平台。它不替代物业已有的ERP、道闸、门禁——它在这些系统之上建立一层制度规则层：让每一次服务都有证据、每一次履约都有记录、每一次违约都有后果。

核心比喻

给社区装一套「制度交通规则」——不是摄像头抓违章，而是让每个人知道规则、遵守规则、违约有记录。物业是「路面」，数治理方是「交规+驾照分」。

理论底盘

收费秩序 = 正当性 × 履约可信度 × 价值感知度 × 守约共识度 × 分类精准度。任一因子趋零，整体崩塌。传统物业只做最后一个（且用错了方法），数治理方五个因子同时做功。

三种部署模式

● 当前

P1 物业入口模式

纯物业通道，工单优先切入。物业公司授权，客服以物业名义接触业主——建工单、做回访、记标签。15个P1字段驱动，不依赖小程序行为数据。

○ 规划

双轨过渡模式

小程序上线后，📱行为轨道 + 🎧客服轨道并行，双轨独立计算后OR合并。适用退管物业交接期——旧数据不丢、新数据续上。

○ 规划

全模式（在管）

六端全开，AI六类自动分类+信号强度+交叉模式+响应级别R0~R4+数字秘书SaaS。五因子同时做功，覆盖业主大会→物业→业委会→社区全链路。

模块A：分类引擎 4场景

数治理方的核心AI能力——基于双轨数据的六类业主自动分类与信号强度计算。

场景名称描述

七 核心基础设施

横跨六端的三套底层系统——分类判定 + 双轨数据 + 数字秘书

业主分类系统 六类判定

数治理方的核心算法——F/E/A/B/D/C 六类业主精准画像，基于实际交互数据实时判定，不是静态标签。

分类名称判定条件
F历史复杂型标签含诉讼/信访/媒体/公安关键词 → 独立判定通道（不参与E~C流水线）→ 最高响应级别R4 → 客服/物业/业委会三端同步标红
E对抗失信型拒接≥3次 或 攻击性语言 或 差评无理由 → 合并对抗信号 → 响应级别R3 → 话术引导：不说教、不施压、记录诉求为主
A合理争议型有未闭环工单 + 业主明确提出服务问题 → 暂停催缴 → 优先解决争议 → 工单闭环后自动重新分类 → 响应级别R3（工单驱动）
B现实困难型业主表达经济困难（大病/失业/低保/单亲…）→ 标记困难 → 差异化方案（分期/减免申请）→ 不适用标准催缴策略 → 响应级别R2
D惯性失约型无争议但承诺≥2次未兑现 → 失约计数递增 → 衰减：7天-1/28天归零/登录小程序即消除 → 核心指标：承诺兑现率 → 响应级别R2
C观望拖延型无明确信号 → 按通话结果细分为C1~C6子类型（已接通无争议/已接通有争议/未接通/空号/号码错误…）→ 兜底分类 → 响应级别R0~R1

八 独有核心能力

为什么别人做不了——数治理方的六重壁垒

📐

五因子乘法模型

收费秩序 = 正当性 × 履约可信度 × 价值感知度 × 守约共识度 × 分类精准度。传统物业只做「分类」一个因子——且用催收代替分类，方法全错。数治理方五个因子同时做功，任一因子趋零则整体崩塌。

🔀

双轨数据架构

📱小程序行为轨道 + 🎧客服通话轨道独立计算，OR合并后走统一判定流水线。每条信号标注数据来源，双轨交叉验证——一条轨道的数据污染不会污染另一条。这是工程壁垒，不是功能点。

🏷

六类精准分类

F·历史复杂型 / E·对抗失信型 / A·合理争议型 / B·现实困难型 / D·惯性失约型 / C·观望拖延型。基于实际交互数据实时判定，不是静态画像。六类各有独立响应策略——同一句话对E类和对B类完全不同。

⚖

制度型治理（不是催收）

禁滞纳金威胁、禁门禁恐吓、禁信用施压。客服只做三件事：引导看服务记录、记录诉求、确认工单闭环。把焦点从「欠多少钱」转移到「遇到什么问题」——这是理念壁垒，竞品抄不走。

👩‍💼

数字秘书 SaaS 多小区

秘书不必是业主——36号文第4条vs第6条立法有意区分 + 沪住建建议复〔2018〕23号明确「可以聘请专职秘书」。一个秘书可服务多个小区，SaaS模式低成本覆盖。这是法律+商业双重壁垒。

🔌

开放端口架构

六端通过 ecosystem-bridge.js 跨端通信，业委会/社区/街道可独立接入。不是封闭的物业SaaS系统，是社区治理的开放基础设施层——灵石的摄像头能接进来、物业的ERP能接进来、政府的网格系统也能接进来。
